# Architecture

> **English** · [Español](ARCHITECTURE.es.md)

How batten is put together, and why each piece is where it is. This is the entry point to the
code: if you are about to change something, start here and you will know which of the sixteen
packages owns it.

For what batten *does*, read the [README](../README.md). For how to install it,
[INSTALL](INSTALL.md). This document assumes you have both.

---

## The thesis, because it decides every boundary below

**A rule a document can only ask for, a hook can impose.**

Every serious team writes its process down — phases, review gates, "two agents never touch the
same file", "never approve without evidence" — and then an agent ignores it and *nothing happens*.
No error, no denial. The rule was a sentence, and a sentence cannot stop a `git commit`.

batten turns that document into **data** and enforces it with Claude Code hooks. That single
sentence explains the whole shape:

| the thing | what it is | where it lives |
|---|---|---|
| **the spec** | your process, declared as data | `batten.yaml` in your repo, parsed by `internal/spec` |
| **the enforcement** | a binary that answers hook payloads on stdin | `cmd/batten` + `internal/hooks` |
| **the delivery** | the Claude Code plugin: hooks, commands, skills, MCP | `plugin/claude-code/` |
| **the record** | what actually happened | SQLite, `internal/store` |

**batten does not orchestrate.** It never launches an agent, never routes a model, never runs your
loop. That is a design decision, not a gap, and it is why `models.tiers` and the `resources:` block
were *deleted* from the spec rather than implemented: they promised an orchestrator that does not
exist. Anything that would require batten to run your workflow is out of scope by construction.

## The two denials

Everything else serves these. If you are reading the code for the first time, read these two paths.

### 1. The verdict gate — `internal/hooks/hooks.go`, `verdictGate`

A `git commit` is denied unless the work item has a verdict envelope citing evidence. Where a gate
declares `checks:`, it needs **two** verdicts from **two different producers**: one batten
generated by *running* the checks (`batten check`), and one a reviewer wrote judging the work
against its acceptance criteria. Neither substitutes for the other.

The decision order matters and is easy to get wrong:

```
destructionGuard      (unattended rule 1 — first, because its mistake is unrecoverable)
  → bashWriteGuard    (a shell command writing a file it does not own)
    → verdictGate     (the commit itself)
      → budget        (a run that blew its ceiling should not quietly land)
```

`commitTarget` answers "which unit is this commit FOR", and the **commit message outranks the
session binding**. On trunk-based development the branch names nothing, so the message is the only
signal there is. Both the gate and the close path go through that one function — they used to
answer it differently, and that disagreement was a real defect.

### 2. The write-set guard — `internal/hooks/hooks.go`, `writeSetGuard`

Running four agents at once is only safe if they cannot land on the same file. "They won't,
because the plan says so" is a hope; the guard is what turns it into a property, and the property
is what lets you fan out at all.

It has three reaches, and the third exists because the first two have a ceiling:

| reach | mechanism | limit |
|---|---|---|
| `Write`/`Edit`/`NotebookEdit` | exact path match against the claimed write-set | none |
| `Bash` | parses the command (`internal/hooks/bashwrite.go`) | **cannot see inside a heredoc, a Makefile target, or a `go run`** |
| after the fact | `batten scan-diff` asks git what changed | needs an anchor |

That middle limit is **declared, not hidden**: no shell parser reaches inside a python heredoc, and
putting deeper heuristics on the critical path is what this project learned not to do without
measurement. `scan-diff` is the structural complement — git cannot be fooled by a heredoc.

## The hooks

`plugin/claude-code/hooks/hooks.json` declares **8 entries** across **6 events**. Seven invoke the
binary; the eighth is the bootstrap, which is shell form because it has to run when the binary does
not exist yet.

| event | what it decides |
|---|---|
| `SessionStart` | installs the binary (bootstrap), then injects the phase briefing: what the phase reads, whether it fans out, what its gate refuses, the diff scope, and **whether the gate is governing anything at all** |
| `PreToolUse` | the two denials, in the order above |
| `PostToolUse` | records what happened; closes a run when its commit lands |
| `SubagentStart` / `SubagentStop` | the run graph's nodes and edges |
| `Stop` | end-of-turn accounting |

**The one thing to know about reading hook output:** silence is *not* evidence of allow. `batten
hook` prints nothing and exits 0 for at least six different reasons — allow, no spec found, a store
failure, malformed stdin, a recovered panic, an unknown event. Every test in this repository that
claims something was allowed carries a **positive control**: the same payload with one field
changed so that a denial is mandatory. If the control is also silent, the hook never engaged and
the "PASS" proved nothing.

## The packages

Sixteen under `internal/`, plus `cmd/batten`. Each holds one rule.

| package | owns | the rule it holds |
|---|---|---|
| `hooks` | the two denials, the briefings, the envelope | fail open, but never quietly |
| `store` | SQLite: runs, verdicts, write-sets, events, criteria, scans | migrations are **expand-only** |
| `spec` | `batten.yaml`: parse, validate, refuse | a spec that permits an evidence-free approval does not load |
| `mcp` | the MCP server the model queries | answer for ONE phase, not the whole document |
| `gitx` | every `git` shell-out | a failure returns an error, never an empty list |
| `scan` | reading a repo it has never seen, to propose a spec | read the backlog before the branch names |
| `plan` | resolving `unit.plan` + `unit.locator` into acceptance criteria | criteria are data, not prose |
| `canvas` | the run graph as JSON Canvas and self-contained HTML | never invent an edge the schema has no relation for |
| `usage` / `statusline` | the token ledger and the rolling-quota ceiling | an unmeasurable quantity reports as unavailable, never as 0 |
| `vault` / `export` | Obsidian output | honour the declared export list, nothing more |
| `install` | what ships and whether the receiving machine can run it | the binary must land where the hooks look |
| `discovery` | finding skills, agents and rules already in the repo | complement the process that exists; never overwrite it |
| `tui` / `render` | terminal surfaces | the same number must render the same way everywhere |

`cmd/batten` is the CLI: 28 subcommands over 29 `switch` arms (`version` has three spellings). It
is deliberately without cobra — zero CLI dependencies. At 2600+ lines it is the largest single
file in the repo and a known refactor candidate; it is not urgent, because a file-per-command split
is all risk and no observable behaviour.

## The record

One SQLite database, at `~/.batten/batten.db` unless `BATTEN_DB` says otherwise.

That path is deliberate and it cost two bugs to learn. The state does **not** live in
`${CLAUDE_PLUGIN_DATA}`: hook processes have that variable and your terminal does not, so a path
that depends on the environment splits the state into two databases — the TUI says "no runs" while
the hooks happily write runs somewhere else. And `${CLAUDE_PLUGIN_ROOT}` is forbidden in any case:
it is wiped on every plugin update.

The tables that carry decisions:

- **`runs`** — one per work item per attempt. Carries the anchor (`base_sha`), the worktree, the
  enforcement mode and the mode flag for unattended runs.
- **`verdicts`** — with `source` (`agent` vs `batten`) and `target_digest`, the fingerprint of the
  tree the verdict was made **about**. That second column is what makes "verified" mean verified
  against *this* tree rather than against whatever existed when the checks ran.
- **`writesets`** — who claimed what. Never deleted, which is what makes the over-declaration
  metric computable at all.
- **`events`** — the replay log, written **after** dispatch, carrying the decision, the reason and
  the rule. Before that it recorded the incoming payload and nothing batten ever *did*, so "how
  many commits did you deny this week" was unanswerable.
- **`scans`** — one row per `scan-diff`, so the write-set contrast becomes a history rather than a
  line of stdout.

Migrations are expand-only: add a column, add a table, never take one away. Two batten binaries
routinely share one database — the one the plugin installed and whatever is on your PATH — so a
migration that dropped anything would leave the older binary reading a file the newer one had
already changed, inside a hook, where a failure is indistinguishable from silence.

## The guards that hold the code honest

This is the part most codebases do not have, and it is worth understanding before you add a
feature — several of these will refuse it.

| guard | what it imposes |
|---|---|
| `TestEveryDeclaredFieldHasAConsumerOrIsDeclaredFuture` | every `batten.yaml` field has a production consumer, or an explicit entry with a reason. **The list is empty** — no field is declared and unread. |
| `TestEveryMigrationIsAdditive` | migrations never drop, rename or delete |
| `TestEveryUnattendedRuleIsMechanicalOrRegisteredAsProse` | every absolute rule of `/batten-night` has a mechanism whose identifier is *used*, not merely declared |
| `TestEveryEdgeRelationReadHasAProducer` | every `edges.rel` a surface reads has something that writes it |
| `TestTheSpecsThisRepoShipsHaveNoDeadKeys` | the published schema and the shipped examples cannot contradict each other |
| `TestNoPrivateProjectTokensAreTracked` | the private repo batten was field-tested against is not named anywhere, including inside the generated graph |
| `TestNoCommentPointsAtADocumentThatIsNotHere` | no tracked file cites a section of a document a clone does not receive |
| `TestEveryCommandRefusesToRunWithoutTheBinary` | every `/batten-*` command's first bash block preflights the binary |
| `TestEveryDocumentThatDrivesAVerdictNamesBattenCheck` | any document that walks an agent to `batten verdict` also names `batten check` |

They exist because a field test found 52 defects in a project with a green suite: **the tests
verified that the code did what it does. Nothing verified that the spec promised only what the code
does.** Each guard turns one recurring class of that into a denial.

## Distribution

The plugin ships **without** a binary — they bloat the repo and go stale. A `SessionStart` hook
runs `scripts/bootstrap.sh` (or `bootstrap.ps1` on Windows without Git Bash), which fetches the
static binary for the platform from the GitHub Release into `${CLAUDE_PLUGIN_ROOT}/bin/batten`.

That path is not a preference. `hooks.json` names it seven times, `.mcp.json` once, Claude Code
puts that directory on PATH — which is what makes the bare `batten` in the `/batten-*` commands
resolve — and `batten doctor` inspects exactly that file to answer "is the gate running?". A binary
anywhere else is a binary nothing invokes.

**One part of the bootstrap fails closed, and only one:** the sha256 check against the release's
`checksums.txt`. Everything else in that script is best-effort, because a bootstrap must never
break a session. Not this: the file being checked is about to be executed by seven hooks and an
MCP server, so installing it unverified is remote code execution by download. A wrong hash, an
unreachable `checksums.txt`, and a machine with no sha256 tool are the same sentence — nobody can
vouch for these bytes — and get the same answer.

It still exits 0. `hooks.json` dispatches `bash bootstrap.sh || powershell bootstrap.ps1`, so a
non-zero exit means "there is no bash", not "the download was bad".

## Where to start reading

| if you want to understand… | read |
|---|---|
| the commit gate | `internal/hooks/hooks.go` → `verdictGate`, `gateShortfall`, `commitTarget` |
| the write-set fence | `internal/hooks/hooks.go` → `writeSetGuard`, then `bashwrite.go` |
| what a spec may declare | `internal/spec/spec.go`, then `batten.schema.json` |
| what is recorded and why | `internal/store/store.go` — the migration comments are the history |
| what ships to a user | `plugin/claude-code/` — hooks, commands, skills, `.mcp.json` |
| whether it actually works | `scripts/matrix-replica.sh` (41 assertions) and `scripts/matrix-demo.sh` (26) |

The commit messages in this repository are long on purpose. Where a comment says *why*, the
commit that introduced it usually says *what it cost to find out*.
